# Phase 6 — Markdown Synchronization

Status: **Complete**

## Goal

Add TreeMark's safe Markdown synchronization capability.

By the end of this phase, a user should be able to point TreeMark at an existing Markdown file containing exactly one valid TreeMark marker pair and update only the content between those markers with freshly generated tree output.

This phase builds on the completed Phase 5 pipeline:

```text
CLI arguments
→ scanner
→ TreeNode
→ renderer
→ generated string
```

and adds:

```text
existing Markdown target
→ marker validation
→ section replacement
→ safe write
```

This phase does not yet implement stale-output comparison with `--check`.

---

## Locked MVP Contract

Default markers:

```html
<!-- treemark:start -->
<!-- treemark:end -->
```

Representative document:

```md
## Documentation map

<!-- treemark:start -->
<!-- Generated by TreeMark. Do not edit manually. -->

- **guides/**
  - [setup.md](docs/guides/setup.md)

<!-- treemark:end -->
```

Rules:

- Both markers must already exist.
- Each marker must appear exactly once.
- The start marker must precede the end marker.
- Marker lines are preserved.
- Only content between markers is replaced.
- Missing markers cause failure without modification.
- Duplicate markers cause failure without modification.
- Reversed markers cause failure without modification.
- Automatic marker insertion is not part of the MVP.
- Running the same update twice against unchanged inputs must not cause a second file change.
- Existing newline style should be preserved when practical.

---

## Scope

### 6A — Marker Parsing and Section Replacement

- Define marker constants.
- Read an existing Markdown target.
- Locate start/end markers.
- Validate marker count and order.
- Replace only the content between markers.
- Preserve marker lines exactly.
- Preserve all content outside the marked region.
- Keep synchronization logic independent from CLI parsing and filesystem traversal.
- Add focused unit tests for marker validation and replacement.

### 6B — `--update` CLI Integration and Safe Writes

- Wire `--update <file>` into the completed scanner/renderer pipeline.
- Resolve the update target from the current working directory.
- Automatically exclude an in-root update target from scanning.
- Compute Markdown links relative to the update document location.
- Render ASCII safely when inserted into Markdown.
- Validate the full update target before writing.
- Skip writing when generated content is already current.
- Write through a temporary file and replace the target safely.
- Clean up temporary files after failures.
- Keep stdout clean during successful updates.
- Add end-to-end update tests.
- Verify all CI jobs.

## Synchronization Pipeline

Intended runtime flow:

```text
CLI arguments
    ↓
resolve root + update target
    ↓
validate CLI combination
    ↓
scanDirectory(...)
    ↓
TreeNode
    ↓
render expected tree
    ↓
read update target
    ↓
validate markers
    ↓
build updated document in memory
    ↓
compare current vs updated document
    ↓
unchanged → return success without writing
changed   → safe temporary-file replacement
```

All scanning, rendering, target reading, and marker validation must complete before the existing Markdown document is modified.

## Marker Constants

Use exact MVP markers:

```ts
export const START_MARKER = "<!-- treemark:start -->";
export const END_MARKER = "<!-- treemark:end -->";
```

Marker strings should have one canonical definition.

Do not duplicate literal marker strings throughout the codebase.

## Marker Validation

A target is valid only when:

```text
start marker count = 1
end marker count   = 1
start index        < end index
```

Invalid cases:

```text
no start marker
no end marker
two start markers
two end markers
start marker after end marker
```

Every invalid case must abort before writing.

Error messages should identify the target and the marker problem clearly.

Representative messages:

```text
TreeMark: update target is missing start marker: README.md
TreeMark: update target contains multiple end markers: README.md
TreeMark: TreeMark markers are reversed: README.md
```

Exact wording may be refined during implementation, but normal CLI use must not expose raw stack traces.

---

## Replacement Semantics

Given:

```md
Before

<!-- treemark:start -->
old content
<!-- treemark:end -->

After
```

and generated content:

```md
- **guides/**
  - setup.md
```

the result should be:

```md
Before

<!-- treemark:start -->
- **guides/**
  - setup.md
<!-- treemark:end -->

After
```

Only the interior region changes.

TreeMark must preserve:

- all content before the start marker;
- the start marker line;
- the end marker line;
- all content after the end marker.

TreeMark should not rewrite unrelated Markdown formatting.

---

## Generated Notice

TreeMark always inserts the following notice as the first line inside a
synchronized region:

```html
<!-- Generated by TreeMark. Do not edit manually. -->
```

Locked MVP behavior:

- The generated notice is always the first line inside the managed region.
- A blank line separates the notice from non-empty generated tree content.
- When the generated tree is empty, no extra blank content line is added.

For non-empty generated content, the region is conceptually:

```text
generated notice
blank line
rendered tree
```

The notice is TreeMark-managed content and is regenerated along with the
rest of the marked region.

## Markdown vs ASCII Insertion

### Markdown format

When `--format markdown` is used with `--update`:

- render the Markdown tree directly inside the marked region;
- Markdown file links are relative to the directory containing the update target;
- `--no-links` produces plain file labels.

### ASCII format

The Product Contract requires ASCII inserted into Markdown to use a fenced `text` block.

Representative synchronized region:

````md
<!-- treemark:start -->
```text
guides/
└── setup.md
```
<!-- treemark:end -->
````

Raw stdout ASCII remains unfenced.

The fence is a synchronization concern, not an ASCII renderer concern.

The ASCII renderer should continue returning raw deterministic tree text.

---

## Update Target Resolution

`--update <file>` resolves from the current working directory.

Examples:

```bash
treemark ./docs --update README.md
treemark ./docs --update docs/index.md
```

The resolved update target:

- must exist;
- must be a file;
- must be readable before any write attempt;
- must be automatically excluded from the scan if it lies inside the root.

The scanner should receive a normalized root-relative exclusion and should not know that the path is an update target.

---

## Link Context

For Markdown synchronization:

```text
scan root
+
directory containing update target
→ destination-relative Markdown link base
```

Example:

```text
root:   ./docs
target: ./README.md
→ link base: docs
```

Example:

```text
root:   ./docs
target: ./docs/index.md
→ link base: ""
```

All generated Markdown link destinations must use `/` separators on every platform.

---

## Safe Write Contract

Phase 6 should implement the Product Contract safe update sequence:

```text
1. Resolve and validate paths.
2. Scan.
3. Render expected output in memory.
4. Read and validate the complete target.
5. Compare expected and existing content.
6. Return without writing when unchanged.
7. Write a temporary file in the target directory.
8. Rename the temporary file over the target.
9. Clean up temporary files after failure.
```

Do not perform direct partial writes into the existing target.

---

### Future backup compatibility

The safe-update pipeline should preserve a clear pre-replacement boundary so
future update-target backup support can be added without redesigning the
synchronization flow.

Conceptually:

```text
read + validate target
→ build complete replacement in memory
→ [future optional backup step]
→ temporary-file write
→ replace target
```

Phase 6 does not create persistent backups, but its write architecture should
not make that feature difficult to add later.

---

### User review expectation

Users should review the resulting file or Git diff after every `--update` run
before committing, publishing, or relying on the change.

For Git-managed files, version control should be treated as the primary
durable recovery mechanism. Future TreeMark-managed backups would provide an
additional recovery layer, not replace normal version-control practices.

---

## Idempotence

Running:

```bash
treemark ./docs --update README.md
```

twice against unchanged inputs must result in:

```text
first run  → target may change
second run → target remains byte-for-byte unchanged
```

The second run should not rewrite the file unnecessarily.

This is important for:

- clean Git diffs;
- stable timestamps when unchanged;
- future `--check` behavior;
- CI predictability.

---

## Newline Handling

Existing newline style should be preserved when practical.

At minimum, Phase 6 should explicitly test:

- LF targets;
- CRLF targets where practical/cross-platform-safe;
- exactly one deterministic separator around generated region content.

Do not accidentally convert an entire document's line endings merely because TreeMark updates one region.

---

## Error Behavior

Update failures should:

- be concise;
- identify the update target;
- identify the marker/path problem;
- return operational exit code `1`;
- never print generated tree content to stdout on failure;
- never partially modify the target;
- avoid raw stack traces during normal CLI use.

Representative failures:

- update target missing;
- update target is a directory;
- target cannot be read;
- missing start marker;
- missing end marker;
- duplicate start marker;
- duplicate end marker;
- reversed markers;
- temporary-file write failure;
- rename failure.

## CLI Contract

Phase 6 activates:

```text
-u, --update <file>
```

Representative commands:

```bash
treemark ./docs --update README.md
treemark ./docs --update README.md --format markdown
treemark ./docs --update README.md --format ascii
treemark ./docs --update README.md --no-links
```

Existing invalid combination remains enforced:

```text
--output + --update
→ reject
```

`--check` remains deferred to Phase 7.

Although the parser already recognizes `--check`, Phase 6 must not implement stale-result exit code `2`.

## Definition of Done

Phase 6 is complete when:

1. `treemark <root> --update <file>` updates exactly one valid marked region.
2. Marker lines and all surrounding Markdown content are preserved.
3. Missing, duplicate, or reversed markers fail without modifying the target.
4. Markdown output uses correct links relative to the update document.
5. `--no-links` works for synchronized Markdown output.
6. ASCII update output is inserted as a fenced `text` block.
7. Update targets inside the scan root do not include themselves.
8. Unchanged updates do not rewrite the target.
9. Changed updates use safe temporary-file replacement.
10. Failed updates do not corrupt or partially modify the target.
11. Newline style is preserved when practical.
12. Scanner and renderer boundaries remain clean.
13. Phase 7 `--check` behavior has not leaked into Phase 6.
14. Unit and end-to-end tests pass.
15. All GitHub Actions matrix jobs pass.
16. `git status` is clean after the final commit.

- Exit code `2`.
- Automatic marker insertion.
- Multiple independently named marker regions.
- Custom marker strings.
- Watch mode.
- Snapshot/timestamp behavior.
- Mermaid.
- SVG.
- HTML.
- Configuration files.
- `.gitignore` import.
- Symlink traversal.
- Markdown AST parsing.

Any newly discovered feature should be recorded here instead of automatically expanding Phase 6 scope.
